# Touch Bar — requirements (current behavior)

Source of truth for what the Touch Bar must do TODAY (Penknife 1.10; main at f0b637b). The history behind each rule (who asked, when, what was tried) stays in `docs/REQUIREMENTS.md` (R-1, R-4, R-19, R-23, R-25, R-26 and the phase notes; R-2, R-3, R-5, R-9, R-10, R-13, R-30 for single buttons) and `docs/DECISIONS.md`; where they disagree with this file, this file wins. Written 2026-11-18 from the code at f0b637b and those docs: second module of "complete requirements per module + tests that validate them" (user, 2026-11-17), after the microphone pilot. A button whose action belongs to another module is covered here only as a button (when it shows, what it shows, what a tap calls); the action itself is in that module's rules (`docs/requirements/microphone.md` for the microphone) or, until it has a file, in REQUIREMENTS.

**How to use it.** Before changing anything that touches the Touch Bar (its buttons, sliders, layout, step-aside, the game), read the rules of the parts you change. After the change, run `scripts/test.sh` and check EVERY affected rule by its Verify line, not only the new behavior. A new or changed wish → change the rule here, and keep the story in REQUIREMENTS.md.

Code paths are relative to `Penknife/`: `TBM` = TouchBar/TouchBarModule.swift, `BV` = TouchBar/BarView.swift (BarButton, BarView, SliderPanel, EasterEggView, GameSound, BatteryIcon), `BL` = TouchBar/BarLayout.swift, `LC` = TouchBar/LevelControls.swift, `LW` = TouchBar/LevelWatchers.swift, `SG` = TouchBar/SliceGame.swift, `TP` = TouchBar/TouchBarPrivate.swift, `DM` = Modules/DialogsModule.swift, `BS` = Settings/BarButtonsSheet.swift, `SV` = Settings/SettingsView.swift, `MGR` = Core/ModuleManager.swift. "R-26 (11-14)" = the REQUIREMENTS.md R-26 line dated 2026-11-14; "Phase 1/2" = the "Phase 1/2 progress" notes in REQUIREMENTS.md; "D: <title>" = the DECISIONS.md bullet with that bold title.
Verify kinds: **auto** (unit test as the code is today) · **auto after refactor** (seam named; see §4) · **manual** (the user's normal action only) · **log** (`/usr/bin/log show --last 1h --predicate 'subsystem == "Penknife" AND category == "TouchBar"' --style compact`; the step-aside lines are debug level: `/usr/bin/log stream --level debug --predicate 'subsystem == "Penknife" AND category == "Dialogs"'`).
Count (2026-11-18, step B done: S1–S6, B-5, B-6, B-7 and O-7): 63 rules = 36 auto (all tested) · 0 auto after refactor · 1 log · 26 manual.
**Tests:** `PenknifeTests/TouchBarRulesTests.swift`, run with `scripts/test.sh` like the microphone's, each named after its rule ("TB-37 …"); TB-63 is the catalog test "MIC-71 TB-63" in `MicrophoneRulesTests.swift`. Never call `TouchBarModule.start()` from a test without a fake presenter (`TouchBarRulesTests.makeBar`): this Mac has a Touch Bar, so the test host would cover the user's real bar.

## 1. Rules

### A. Presence and presentation

- **TB-01** The bar runs only on a Mac with a Touch Bar: Apple silicon models expose the `dispdfr` IORegistry node; Intel models are matched by `hw.model` (`MacBookPro15,*`, `MacBookPro16,1`, `16,2`, `16,4`). Without one the module starts nothing (no bar, no listeners, no timers), and Native Dialogs watches nothing either (TB-46). Settings shows both as unavailable there (O-7, variant A, user 2026-11-18): the sidebar rows stay at the end of the modules, dimmed to 50 % with a gray tile, VoiceOver value "Unavailable" / "No disponible"; each page shows its switch off and disabled (the saved value is not changed, so it applies again on a Mac with a Touch Bar), the note "This Mac has no Touch Bar." / "Este Mac no tiene Touch Bar." (Touch Bar) or "Only useful on Macs with a Touch Bar." / "Solo es útil en Macs con Touch Bar." (Native Dialogs) with an `info.circle`, and its options dimmed. The launch argument `-pretendNoTouchBar` makes this Mac behave as one without a Touch Bar (checks and screenshots).
  Source: R-1 "Only active on Macs with a Touch Bar"; D: Touch Bar presentation · Code: TP:hasTouchBar, TBM:start; Core/Module.swift:needsTouchBar, isAvailable; SV:sidebar, ModuleDetail · Verify: **auto** — `isAvailable(hasTouchBar:)` (test "O-7 TB-01 TB-46 …"); (S1) — `hasTouchBar(dispdfr:model:)`: node → true without reading the model; no node + "MacBookPro16,2" → true; no node + "MacBookPro16,3" or "MacBookAir10,1" → false; manual — on this Mac the bar shows at launch; with `-pretendNoTouchBar` the two rows read "Unavailable" and the pages look as above (checked 2026-11-18, build 128); (S6) a fake presenter with no Touch Bar: start holds nothing and presents nothing.
- **TB-02** Apple's private Touch Bar calls (DFRFoundation functions through `dlsym`, NSTouchBar / NSTouchBarItem class methods through `class_getClassMethod`) are looked up at runtime: no bridging header, no MTMR code. If the present or minimize call is missing, the module logs `Private Touch Bar calls not found` and does nothing else (no crash).
  Source: R-1 (own implementation); D: Touch Bar presentation; D: Private APIs can't be removed; D: License · Code: TP (all), TBM:start · Verify: **auto** (S6) — a fake presenter without the calls: start holds nothing and presents nothing; log — the TouchBar log is empty on macOS 26.6 (the line appears only if a macOS update removes the calls).
- **TB-03** Penknife's bar covers the whole Touch Bar as a system-modal bar (placement 1: the Control Strip is hidden) with one custom item: a 1004 × 30 pt view of equal-width buttons 6 pt apart. A tray button with the Penknife glyph (VoiceOver "Penknife") is put in the Control Strip, with no close box; tapping it brings the bar back after the system hid it.
  Source: D: Touch Bar presentation; R-21 (one glyph for the Touch Bar tray) · Code: TBM:start, present; TP:addTrayItem, present; BV:BarView.init · Verify: manual — look at the Touch Bar: only Penknife's buttons, no Control Strip.
- **TB-04** The bar is presented again whenever any app becomes active and after the Mac wakes (the clock is redrawn then too), unless it is stepped aside for a dialog (TB-43). So an app's own Touch Bar controls never replace it, except during a dialog.
  Source: D: Touch Bar presentation ("Re-presented on app activation and wake") · Code: TBM:start (activation and wake observers), present · Verify: manual — switch to Safari, then to Finder: Penknife's bar stays.
- **TB-05** No MTMR handling: Penknife doesn't detect, warn about or quit MTMR (or any other app with a system-modal bar). The user quits it; with both running they replace each other and Penknife takes the bar back at every app switch (TB-04) (open question O-10).
  Source: Phase 2 "MTMR must be closed while Penknife's Touch Bar is on"; R-1 (MTMR uninstalled after phase 2) · Code: none (in `Penknife/`, "MTMR" appears only in comments) · Verify: manual — code review: nothing looks for MTMR.
- **TB-06** On a Mac with a Touch Bar the menu bar readings (weather, Mac temperature, speed test; R-30) are off by default (`menuBar.show.<kind>` defaults to "this Mac has no Touch Bar"); each can still be turned on.
  Source: R-30 (11-17) "ON by default on Macs without Touch Bar, OFF by default on Macs with one" · Code: App/MenuBarReadings.swift:shownByDefault; SV:MenuBarToggle · Verify: **auto** (S1) — `shownByDefault(hasTouchBar:)` and `isShown(_:in:hasTouchBar:)` on an empty suite → false with, true without; manual — fresh settings on this Mac: no weather or temperature item in the menu bar.

- **TB-10** How a button draws: an SF Symbol at 16 pt regular in the button's tint, an optional text at 15 pt, or a number at 14 pt over its unit at 9 pt (55 % opacity) drawn as one image (speed test). - **TB-13** VoiceOver: every button has a label that states its value or state in words (given with each button below); the slider is named after its control, the ✕ is "Close", the game is "Slicing game". ### D. Sliders

- **TB-29** Brightness, keyboard light and volume open a slider from their button: rightwards when the button's center is in the bar's left half, else leftwards. Slider and ✕ are one gray element (28 % white, 6 pt corners), full bar height, as wide as the button plus 300 pt (at most the bar); the ✕ (44 pt) sits on the button's side, so tapping the same spot again closes it. The knob follows the finger's x clamped to the track (past the end = 100 %, before the start = 0 %) and stays where the finger lifts, inside the slider or not (B-12).
  Source: R-1 (11-13) sliders; Phase 2 "Sliders approved by the user" · Code: BV:BarView.openSlider, SliderPanel, TintedSliderCell · Verify: **auto** (S3) — `BarView.sliderPlacement(buttonFrame:barWidth:)`: center left of the half → opens right, exactly at the half → left; width = min(button + 300, bar); manual — tap volume (right half): the slider grows to the left.
- **TB-30** While a slider is open every button is hidden (they keep their places) and only the slider shows.
  Source: Phase 2 "while one is open, all other buttons are hidden" · Code: BV:setButtonsHidden · Verify: manual — open the brightness slider: no other button on the bar.
- **TB-31** Closing: the ✕ always closes it.   Source: R-1 (11-13) "closes ~0.4 s after release (at most 1 s after the last change) or after 4 s if untouched; ✕ closes it"; R-19 "Auto-closing elements (sliders, date) have a setting" · Code: BV:SliderPanel.scheduleClose, changed, TintedSliderCell.stopTracking, setButtons, playGame, playEasterEgg; TBM:minimize, stop · Verify: **auto** (S3) — `SliderPanel.closeDelay(after:autoClose:)`: open 4, change 1, release 0.4, nil when off; manual — drag the volume and lift: it closes a moment later.
